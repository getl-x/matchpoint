# 赛点视觉精修（广播风）设计

日期：2026-10-06
范围：`styles.css` 一个文件。不改 DOM、类名、`data-*` 契约，不改布局栅格与断点，不引入字体文件、构建步骤或依赖。

## 目标与取舍

用户在「精修 / 视觉重构」中选了**精修**，在「电竞转播风 / 精致编辑风 / 保留柔和紫 / 中性底 + 每游戏一色」中选了**电竞转播风**，并要求保留紫色识别。

两者的调和方式是**分工而不是折中**：紫色从「铺满全站的淡紫底色」收缩为高饱和的电信号紫，只用于导航选中态、主按钮、焦点环、关键数字与互动元素；页面底色换成冷中性灰。原先「发闷」的直接来源是 `--surface-raised:#faf8fe`、`--surface-soft:#f1edf8`、`--border:#e7e1ef` 这类淡紫表面色，以及十几个近似浅紫同时出现却没有强调层次。

## 诊断（都是可核实的）

| 问题 | 证据 |
|---|---|
| 正文字号过小 | 6–10px 共 219 处声明用在赛事名、状态、时间、队名上 |
| 对比度不达标 | `--text-muted:#958aa6` on `--bg:#f8f9fc` = 3.09:1；`--accent:#8a6bc7` on 白 = 4.19:1；手机端赛事名 `#a58fb6` on 白 = 2.77:1（AA 需 4.5:1） |
| 没有真正的令牌层 | 389 个不同颜色值，绝大多数只用一次；`:root` 只声明 6 个变量 |
| 深色模式靠逐组件补丁 | 约 30 条 `html[data-theme="dark"] .选择器A,.选择器B,…` 覆盖块，每条列十几个选择器 |
| 浅色主题被追加了三代 | `.page-heading p{color}` 被写了 3 次（`#96909f` → `#8b8296`），只有最后一次生效 |
| `:root` 被声明两次 | 两个浅色令牌块，后来者会赢回旧色板 |
| 圆角与阴影没有系统 | 20 种圆角取值；11 个阴影全部偏紫 |
| 没有等宽数字 | 比分与时间列栅格不齐 |
| 字体没落地 | 写了 `Inter` 但从未加载，实际落到 Segoe UI / 微软雅黑 |

## 令牌层

`light`（`:root`）与 `dark`（`html[data-theme="dark"]`）各持一套完整取值。分「表面 / 文字 / 强调 / 状态 / elevation / 圆角 / 字阶 / 组件面」八组，组件面包含 hero、直播卡、LIVE 药丸、安装卡、Apex 徽记、顶栏、移动底栏、待定徽标、浮层、遮罩、网格点阵。

冷中性灰，色相约 228°，饱和度 ≤ 8%：

| 令牌 | light | dark |
|---|---|---|
| `--bg` | `#f1f3f7` | `#0b0d12` |
| `--surface` | `#fff` | `#14171f` |
| `--surface-raised` | `#eef1f6` | `#1a1e28` |
| `--surface-soft` | `#f5f7fa` | `#222732` |
| `--border` | `#dde2ea` | `#242a37` |
| `--text` | `#12151c` | `#e8ebf2` |
| `--text-secondary` | `#4d5766` | `#a5afc1` |
| `--text-muted` | `#5f6a7d` | `#79849a` |

强调色拆成两个令牌，各司其职（这是让紫字可读的关键）：

| 令牌 | light | dark | 用途 |
|---|---|---|---|
| `--accent` | `#5b3fd6` | `#6d4fe0` | 填充、描边、图形、选中底 |
| `--accent-text` | `#4a32a8` | `#b6a2ff` | 所有紫色文字 |
| `--accent-soft` | `#ece7fb` | `#1e1a33` | 淡紫底（比原 `#f1edf8` 更冷更干净） |
| `--accent-contrast` | `#fff` | `#fff` | 强调底上的文字 |

实测对比度：

| 组合 | 改造前 | 改造后 |
|---|---|---|
| `--text-muted` on `--bg` | 3.09:1 | 4.92:1（另在白色卡面 5.46:1） |
| `--accent` on `--surface` | 4.19:1 | 6.72:1 |
| 手机端赛事名 on `--surface` | 2.77:1 | 7.32:1 |

字阶：`11 / 12 / 13 / 14 / 15 / 16 / 18 / 22 / 28px`，**正文下限 11px**。6–7px→11px，8–10px→12px，11–12px→13px，13px→14px。

圆角：`--r-xs:4 / --r-sm:6 / --r-md:8 / --r-lg:12 / --r-xl:16`，比原先的统一 16px 利落。阴影：`--e1`（贴地）/ `--e2`（浮层）/ `--e3`（弹窗），冷色 `rgba(11,13,18,…)`；深色模式不用发光，改用卡顶 1px 内高光加更深投影。

## 实现方式

`styles.css` 是 161 行、98KB 的紧凑手写风格（有 5 行特别长），因此改造用**替换表 + 脚本**完成而不是手抄，规则结构与格式原样保留、可逐条核对：

1. 删除 31 条 `html[data-theme="dark"]` 逐组件覆盖块（仅当该规则的所有选择器都是深色作用域时才删）。
2. 人工覆盖表处理品牌强调色、强调底上的白字、状态色、渐变、阴影与焦点环。
3. 按角色自动映射颜色：色相在紫罗兰带（230–310°）且色度 ≥0.22 → 强调色；紫罗兰带内低色度 → 中性灰按属性与亮度落到表面 / 文字档；紫罗兰带外且有色度 → 判定为语义色（状态绿、琥珀、红、teal、归档与提醒）**保持原值不动**。
4. 字号、圆角、阴影按表替换。
5. 补写基础规则中缺失的声明（导航选中态文字色、hero 图片滤镜、tabular-nums）。
6. 删除同 `@media` 上下文内同选择器同属性被后续世代覆盖的死声明；令牌块永不参与去重。

## 验证

- `npm test`（161 项，改造前后一致）与 `npm run check:syntax`（76 个文件）通过。
- 结构自检脚本比对改造前后的选择器集合：仅消失被删除的 31 条深色规则，无其他丢失、无新增，花括号平衡。
- 独立浏览器校验（替代失效的仓库套件）：4 页面 × 2 主题 × 6 档宽度共 48 组合无横向溢出；32 项对比度实测全部达 AA；无低于 11px 的可见文字；tabular-nums 生效；逐张复核浅色 / 深色 / 手机截图。
- PWA 缓存版本 `matchpoint-v15-atomic-updates` → `matchpoint-v16-broadcast-visual-refresh`。

## 已知偏差

- **未加赛程行左侧状态色带**。方案里提过，实测后放弃：面板自身有内边距，色带会与面板边缘脱开而显得悬空；状态已由着色状态文字与直播卡承担；且该选择器需要 `:has()`。可用 `.map-match:hover` 已有的 `inset 3px 0 var(--accent)` 写法作为后续低成本方案。
- **未合并末尾的多个 `@media(max-width:640px)` 块**。相邻合并没有问题，但这几块并不相邻，合并会改变级联顺序。真正的问题（同属性被反复覆盖）已由死声明清除解决。
- **未降低 TBD 卡片高度**。图布局有专门的重叠 / 裁切断言，改高度风险高于收益；改为未定队伍徽标虚线描边来传达同一语义。
- **`:focus-visible` 并非全新**。原本已有 `outline:2px solid #aa97e1`（约 2.5:1），本次只是换成达标的发光紫（浅色 6.7:1）。
- **`--text-faint` 档被并入 `--text-muted`**。原方案保留了四档文字，但最浅一档在白底只有约 3:1，无法同时满足「有层次」与「达 AA」，选择保证可读。

## 顺手发现的既有问题（未修改）

`tests/browser-check.cjs` 与 `tests/diagram-layout-check.cjs` 使用 `locator('.theme-toggle')`，而 `.theme-toggle` 现在同时匹配「更新应用」与主题两个按钮，触发 Playwright strict mode；`tests/team-logo-browser-check.cjs:27` 的比分断言也与样式无关。已用原始 `styles.css` 复现完全相同的三处失败作为对照，说明这是 `main` 上既有的测试失效，不是本次改动引入。本次遵守「只动 `styles.css`」的范围，未修改测试；建议单独修一次，让整体浏览器验收重新成为发布关卡。

# 第二轮：广播风形制层（2026-10-06 追加）

上一轮交付后用户反馈「和之前没什么区别」「看不出电竞转播风」。复盘结论成立：**转播 UI 的辨识度主要来自形制，而不是配色**。上一轮只把圆角从 16px 收到 12px，投影、渐变面板、柔和边框全部保留，所以观感变化只有 5%。本轮重做形制。

## 用户新增的三个决定

| 问题 | 选择 |
|---|---|
| 形制语言 | **切角**：直角 2px + 关键组件 `clip-path` 斜切一角 |
| 强调色策略 | **游戏色 + 队伍色驱动数据区**，紫色退到品牌位 |
| 改动自由度 | 允许在 JS 里补 CSS 变量（类名、DOM 结构、测试选择器不变） |

## 切角的技术约束（决定整套做法）

`clip-path` 会裁掉描边、投影**以及 `outline` 焦点环**。直接把切角写在元素上会破坏键盘可达性。因此：

```css
.schedule-hero::before{content:"";position:absolute;inset:0;z-index:-1;
  background:var(--hero-bg);
  clip-path:polygon(0 0,calc(100% - var(--cf)) 0,100% var(--cf),100% 100%,0 100%)}
.schedule-hero{isolation:isolate}
```

切角画在 `::before` 装饰层上，元素本体不裁切：盒模型不变、布局不受影响、焦点环完整。代价是**斜边无法带 1px 描边**（描边会被一起裁掉），所以切角组件不描边，靠填充与底色分层——这与真实转播画面一致（平面填充，不靠描边）。

## 形制与颜色分工

- 圆角 1/2/2/2/3px；投影 `--e1:none`（卡片零投影），只留浮层/弹窗的 `--e2`/`--e3`。
- 所有渐变面板改平面填充；hero 改为平面板 + 135° 斜纹，奖杯降为 9% 灰废水印，装饰圆环/星芒/斜置文字隐藏。
- 游戏色提饱和：无畏契约 `#ff4655`、CS2 `#f0a739`、英雄联盟 `#22b3c9`、Apex `#e3493f`。
- **游戏色与队伍色只做图形，不做正文颜色**——这是保住上一轮 AA 成果的关键约束。
- 状态改实心 `--chip-*` 色块（主题无关，避免深色主题下色块与底色打架）。

## 与方案的偏差（有数据依据）

**队伍色竖条未做。** 实测四个官方来源的 113 支队伍只返回 3 个不同颜色（`#59a9aa`×61、`#e56e87`×33、`#c99b54`×19），是按游戏给的兜底色而非队伍识别色。照做会画出与游戏导轨重复的颜色。因此 JS 注入点由 8 处减为 3 处（赛程行、存档卡、侧栏游戏项的 `--game`），队伍识别交给 Logo 与字重。

**弹窗比分区保持 31px 而非 40px。** 弹窗在 360px 设备上内容宽约 336px，两侧队伍块固定 105px，40px 数字有溢出风险。

## 验证

48 个溢出组合、42 项对比度实测（最低 4.56:1）、字号下限、令牌审计（71 个令牌，无未定义、无未使用）、结构自检全部通过；`npm test` 161 项无回归。详见 `docs/VERIFICATION.md` 同日条目。

# 第三轮：Riot 小组赛改紧凑日程面板（2026-10-06 追加）

用户反馈「CS 的晋级图好看，无畏契约的挺丑的，能改成 CS 这样的吗」。

## 诊断

| 游戏 | 路径 | 结果 |
|---|---|---|
| CS2 | `csBoard` → `layoutSwiss` | 紧凑分组面板 + 晋级名单 + 胜/负流线 |
| Valorant / LoL | `grouped()` → `layoutStageCards` | **每场一张 290×154 大卡**，20 场摊成 3 列卡片墙 |
| Valorant 季后赛 | `grouped()` → `layoutElimination` | 本来就是对的（逐轮淘汰树） |

根因是**布局算法差异**，不是样式问题。数据边界：Riot 侧只有阶段名、日期、状态、比分、BO 数，没有 `groups`、没有轮次、没有 `nextMatch`，所以无法照搬 swiss 的胜负记录分组。

## 方案：按真实比赛日分列的紧凑面板

新增 `layoutStagePanels(name, matches)`，直接复用 CS 那套 `.map-group` / `.map-match` 组件：

- 根节点 = 阶段名；每个比赛日一列一块面板；单日超过 10 场才拆第二列并标「续」
- 面板：标题「第 N 比赛日 / MM月DD日」，右上「N 场」，正文紧凑行，页脚「星期 · n/m 已结束」
- 连线一律 `kind:'membership'`，含义与既有 `layoutStageMap` 一致：**只表示本阶段包含这些比赛，不声称任何晋级关系**
- 组件的可扩展点：`mapNode` 新增可选 `heading` / `sublabel` / `footerLabel`，缺省回落到原逻辑 → **CS 的瑞士轮渲染完全不变**

实时页与档案页同步切换。图表版本 3 → 4，并收敛为导出的 `DIAGRAM_VERSION` 常量（原先两处生产代码硬编码 `!==3`，bump 后会永远判定需要重算并每次读取都重写存档）。`layoutStageCards` 删除，无引用残留。

## 顺带修好的四个测试缺陷

它们都属于「检查从未被执行到」的潜伏问题——`.theme-toggle` 冲突让两条套件都死在第 2 项，后面的检查长期没有运行过：

1. **`.theme-toggle` strict mode**（3 个文件）：该 class 现在同时匹配「更新应用」与主题按钮。改用 `[data-action="theme"]`。
2. **`innerText` 用于断言比分**：`.detail-score>b` 是 `display:flex`，`innerText` 在 flex item 之间插换行（实测 `"0\n:\n3\n已结束"`）。产品渲染正确，是断言用错了 API；改用 `textContent`。
3. **主题变体检查**：`page.reload()` 会把日期筛选重置为「今天」，而当天无畏契约没有比赛 → 行列表为空、`loaded()` 必然超时。改为重载后先断言主题持久化，再恢复日期后断言变体。
4. **离线图标检查**：同一个根因，同样修法。

## 验证

`npm test` 161 项、`npm run test:browser` **27 项**、`test:diagram`、`test:elimination`、`test:logos` 9 项，全部通过。整体浏览器验收自「更新应用」提交引入 selector 冲突以来首次完整跑通。

## 开发期陷阱（非代码缺陷）

`server.mjs` 以进程生命周期缓存 `readAppVersion` 的结果，所以改动 `src/`、`styles.css`、`sw.js` 等 shell 文件后**必须重启本地服务器**——否则 `/api/app-version` 公布的哈希与实际内容不符，Service Worker 安装会因哈希校验失败而静默失败，离线不可用。排查该问题时先怀疑了缓存内容、注册时机，最后用「逐资源比对公布哈希与实际内容」定位。

# 第四轮：CS2「正在进行」不显示（2026-10-06 追加）

用户反馈 `2026 ESL 职业联赛第24赛季` 的 `Spirit vs 1win`（北京 20:00 开赛）在 20:17 仍显示「未开始」。

## 诊断

`server/providers/blast.mjs` 用逐场 `m.isLive` 判定进行中，而实测三个相邻赛事全部 **96 场对阵中 `isLive===true` 为 0 个**。逐场直播端点全部 404。真正可用的信号是赛事列表里的 **`isTournamentLive`**（ESL Pro League S24 为 `true`，全列表唯一），而它在代码库中零引用。

各游戏对比：Riot（LoL/无畏契约）有专用的 `eventState:['inProgress']` 查询——**同类问题早已被专门修过**；Apex 配置了 `inProgress→live` 映射但 EA 当前只发布 `completed`/`pending`，该路径未被真实数据验证过。

## 修复（不违反「未知状态不根据时间猜成 live」）

- 在四个 provider 共用的 `finish()` 出口统一计算 `startOverdue`（宽限 5 分钟）。它只描述**来源数据是否落后于赛程时间**：`status` 一律保持官方原值，并明确排除 `live`/`finished`/`cancelled`/`postponed`。
- 透出 `events[].live`（BLAST 的 `isTournamentLive`）。
- 顺带修掉同类缺陷：仅存在于 `tournamentMatchesPromise` 的比赛原先硬编码 `status:'unknown'`，现按开赛时间区分 `upcoming` / `unknown`。
- 前端：超时比赛的时间格显示「应已开赛」（该处原本是「北京时间」，而区块标题已注明所有时间为北京时间），并带完整说明的 `title`；官方状态徽标保持「未开始」不变。事件选择器与晋级图赛事标题显示「直播中」/「官方直播中」。
- 颜色用 `--match-live-text`（浅色 7.23:1、深色 14.6:1）而非只适合做图形的 `--match-live-tone`（浅色 3.65:1 不达标）。

## 验证

`npm test` 164 项（新增 3 项）、`npm run test:browser` **28 项**（新增 1 项确定性检查：`page.route` 注入一场超时比赛，断言时间格显示「应已开赛」而状态徽标仍为「未开始」）。真实数据实测：ESL S24 `live=true`、2 场超时比赛 `startOverdue=true` 且 `status` 仍为 `upcoming`、**被时间提升为 live 的比赛数为 0**；既有的「not assumed live by wall clock」测试继续通过。截图确认赛程行与赛事选择器的实际渲染。
